# Core Idea

E.g. writing the following code...

```rust
#[blueprint]
struct Root {
    #[slot]
    leaf: Leaf,
}

struct Leaf;
```

This will generate the following code. (All code is subject to change. I only write this to convey my idea. None of this
is meant to be final.)

```rust
trait RootMode {
    type Leaf; // named after the field ident, not its type.
}
struct RootDraft;
struct RootFinal;
impl RootMode for RootDraft {
    type Leaf = Slot<Leaf>;
}
impl RootMode for RootFinal {
    type Leaf = Leaf;
}
type RootBlueprint = Root<RootDraft>;
struct Root<M: RootMode = RootFinal> {
    leaf: M::Leaf,
}
```

Slot is a library struct defined as follows.

```rust
enum Slot<T> {
    Fixed(T),
    Choose(Choice<T>),
}

struct Choice<T> {
    cardinality: Cardinality,
    options: Vec<T>,
}

enum Cardinality {
    Exact(usize),
    AtLeast(usize),
    UpTo(usize),
}
```

The Root struct can be in Draft or in Final mode. In Draft mode its leaf field is a slot, meaning it can either be a
fixed value or a choice. If it's a fixed value, all of Root's fields are fixed and Root<RootDraft> can be resolved to
Root<RootFinal>. If it's a choice, the user must pick one option and the slot will resolve to a fixed value.
Consequently, Root<RootDraft> can resolve to Root<RootFinal>.

The blueprint item attribute is not allowed on a trait, on an enum or on a struct with unnamed fields. The slot field
attribute is allowed on any field within a struct that has the blueprint attribute.

## The blueprint trait

Interacting with any blueprint in an object hierarchy, it can walk through the choices breadth-first. These interactions
are defined in a trait that's provided in the library crate. The Blueprint trait is implemented on a struct during macro
code generation when a struct has the blueprint attribute.

```rust
trait Blueprint {
    type Final;
    /// Returns whether all choices in this hierarchy of blueprints are made.
    fn is_ok(&self) -> bool;
    /// Returns the first choice that has not been made yet, breadth-first.
    fn next_choice(&mut self) -> Option<&mut Choice<T>>;
    /// Turns this blueprint into its final form given all choices were correctly made.
    fn resolve(self) -> Result<Self::Final, ChoiceError>;
}
```

The macro will generate the implementation for this trait. It should only be implemented on the Draft version of thhe
struct.

```rust
impl Blueprint for RootBlueprint {
    type Final = Root;
    // -- snip --
    // Generate this.
}
```

## Slot fields

The slot field attribute is used to denote that in blueprint mode, this field might not yet be finalized. A slot can be
a fixed value, in which case it's finalized. It might also be a choice, in which case, once the choice is made, the
field can "become" finalized by converting the whole blueprint mode struct to its final form.

```rust
#[blueprint]
struct Root {
    #[slot]
    leaf: Leaf,
}

struct Leaf;
```

This code will generate the option for leaf to be a choice. The final user will pick one of N leaf instances. In the
final mode of Root, the leaf field will have that chosen value.

But... slots are not always singular values.

```rust
#[blueprint]
struct Root {
    #[slot]
    leafs: Vec<Leaf>,
}

struct Leaf;
```

When a vec is assigned the slot attribute, the user picks M of N instances. In the final mode of Root, the leafs field
will be a Vec containing all those chosen values. The correct amount of picks to be made is found in the cardinality of
the choice.

> In these code examples, a field with a single value (not a vec) that's a Slot::Choose variant, the domain language
> allows that choice to have a cardinality of AtLeast 2 while the cardinality is de facto exactly one. The final code
> may not allow such disprecancies in the domain language.

The slot field attribute must also be able to convey if the Vec field is a choice that resolves to a vec of a vec of
slots. Imagine we're building a D&D 5e race, the Dwarf. The Dwarf has a list of traits (D&D, not Rust). All these traits
are fixed values except for the Tool Proficiency trait. That trait is a choice between three tool proficiencies. In this
case we have a Vec of Slots that resolves to a Vec of Traits in the final mode. On the other hand, when you create a D&D
5e class, you have to choose your skill proficiencies. You have to choose up to 3 skills from a predefined list of
skills. This is a slot that resolves to a Vec with a choice of higher cardinality.

## Blueprint slots

The type of the field that's annotated with slot might be a blueprint of itself. This means that in draft mode, the
Slot's generic type must be the draft mode of the field type. This also goes for Vec slots, both if it's a Vec of slots
or a Slot that resolves to a Vec.

## Builder

The blueprint attribute must be able to denote if the user wants add builder features to the draft mode. Use the typed
builder from crates.io for this, pin the version. E.g.:

```rust
#[cfg(feature = "builders")]
use typed_builder::TypedBuilder;

#[cfg_attr(feature = "builders", derive(TypedBuilder), builder(mutators(
    pub fn with_trait(&mut self, trait_: Trait) {
        self.traits.push(Slot::Fixed(trait_))
    }
    pub fn with_trait_choice(&mut self, choice: Choice<Trait>) {
        self.traits.push(Slot::Choice(choice))
    }
)))]
#[serde_as]
#[derive(Clone, Serialize, Deserialize)]
pub struct RaceBlueprint {
    #[serde_as(as = "DisplayFromStr")]
    id: RaceRef,
    #[cfg_attr(feature = "builders", builder(setter(into)))]
    name: String,
    #[cfg_attr(feature = "builders", builder(setter(into)))]
    description: String,
    #[serde(with = "serde_untagged_vec")]
    #[cfg_attr(feature = "builders", builder(default, via_mutators))]
    traits: Vec<Slot<Trait>>,
}
```

The typed builder attributes are added by the macro generation as well.
