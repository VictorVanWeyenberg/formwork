# Current State

`Mode` is a trait with associated types. A struct that can be in a `Mode` can have fields with the same types of the
associated types. To do so, add a generic parameter `M` that implements `Mode` and give your field the type
`M::Associated`.

Those associated types are filled in by 2 implementations: `Draft` and `Final`.
`Draft` defines the types of the fields when the struct is not finalized. In this case `Slot`.
`Final` defines the type of the fields when the struct is finalized.

## Problem

`Mode` must be aware of all implementors. When a `Race` implements `Blueprint`, mode must get a `Trait` type. When a
`Class` implements `Blueprint`, mode must get a starting equipment, class level, subclass and feature type. This is poor
architecture.

## Goal

By making `Mode` unaware of the implementors, the `Blueprint` system might be able to become a standalone crate. Structs
would only need to add attributes and no boilerplate.

# Planning

1. The derive macro must be replaced by an attribute macro.

This is needed in order to change the struct, its generics and its fields.

2. `Mode` must be generated by the macro.

This means that each `Blueprint` implementor has its own `Mode` trait and `Draft` and `Final` implementors. The Race
struct will generate a `RaceMode` trait and the `RaceDraft` and `RaceFinal` implementors of that trait.
`RaceDraft`'s types will be slots like the current `Draft` implementor.
`RaceFinal`'s types will be the normal types like in the original struct.

```rust
#[blueprint]
struct Race {
    increase: AbilityScoreIncrease,
    traits: Vec<Trait>,
}
```

Generate with same visibility as the original struct:

```rust
trait RaceMode {}
struct RaceDraft;
struct RaceFinal;
impl RaceMode for RaceDraft {}
impl RaceMode for RaceFinal {}
type RaceBlueprint = Race<RaceDraft>;
```

3. The macro must add the generic parameter to the struct.

The macro is invalid on generic structs or any kind of enums or traits. The macro will add a generic parameter to the
struct `M`. That parameter must implement the respective `Mode` trait and define a default type. E.g.:
`struct Race<M: RaceMode = RaceFinal> { /* -- snip -- */ }`

4. `Slot` fields must be recognized by an attribute.

```rust
#[blueprint]
struct Race {
    #[slot]
    increase: AbilityScoreIncrease,
    #[slots(transitive)]
    traits: Vec<Trait>,
}
```

This is already expanded to:

```rust
struct Race<M: RaceMode = RaceFinal> {
    increase: AbilityScoreIncrease,
    traits: Vec<Trait>,
}

trait RaceMode {}
struct RaceDraft;
struct RaceFinal;
impl RaceMode for RaceDraft {}
impl RaceMode for RaceFinal {}
type RaceBlueprint = Race<RaceDraft>;
```

Now expand it to:

```rust
struct Race<M: RaceMode = RaceFinal> {
    increase: <M as RaceMode>::Increase,
    traits: Vec<<M as RaceMode>::Traits>,
}

trait RaceMode {
    type Increase: Node + From<AbilityScoreIncrease>;
    type Traits: Node + From<Trait>;
}
struct RaceDraft;
struct RaceFinal;
impl RaceMode for RaceDraft {
    type Increase = Slot<AbilityScoreIncrease>;
    type Traits = Slot<Trait<TraitDraft>>;
}
impl RaceMode for RaceFinal {
    type Increase = AbilityScoreIncrease;
    type Traits = Trait;
}
type RaceBlueprint = Race<RaceDraft>;
```

The `slot` attribute means the field also has a mode. The `slots` attribute means this is a collection (one-generic) of
a type that also has a mode. The `slot`/`slots` attribute should trigger generating the associated type in the `Mode`
trait and its implementors. The name of the associated type is the PascalCase of the field name.

In the `Final` implementor, the type is the original type from the input struct. The `trans` predicate field means that
the field type is a `Blueprint` as well on its turn. If `trans`is present for field type`Field`, the type is
`Slot<Field<FieldDraft>>`. The macro will assume ident `Field`+`Draft`exists. If`trans`is not present for field type
`Field`, the type is `Slot<Field>`.

| Attribute  | slot     | ~              | slots               | ~              | slot(transitive)  | ~                   | slots(transitive)   | ~                       |
|------------|----------|----------------|---------------------|----------------|-------------------|---------------------|---------------------|-------------------------|
| Field type | A        | Vec\<A>        | A                   | Vec\<A>        | A                 | Vec\<A>             | A                   | Vec\<A>                 |
| Draft      | Slot\<A> | Slot\<Vec\<A>> | Invalid<sup>1</sup> | Vec\<Slot\<A>> | Slot\<A\<ADraft>> | Invalid<sup>2</sup> | Invalid<sup>1</sup> | Vec\<Slot\<A\<ADraft>>> |
| Final      | A        | Vec\<A>        | Invalid<sup>1</sup> | Vec\<A>        | A                 | Invalid<sup>2</sup> | Invalid<sup>1</sup> | Vec\<A>                 |

**Invalid<sup>1</sup>**: The attribute `slots` is meant for collections.

**Invalid<sup>2</sup>**: A generic object cannot transitively be a blueprint. If this is a collection, you may want to
use the `slots(transitive)` attribute.
